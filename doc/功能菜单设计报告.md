# DBMS 功能菜单设计报告

> 依据当前 `MainLayout.vue`、前端路由和后端菜单权限目录梳理。范围是当前侧边栏的所有可授权、可见菜单；每个菜单均由权限 Key 控制。更新时间：2026-08-30。

## 1. 菜单设计目标

菜单按 DBA 的工作链路组织：**看运行 → 管资源 → 管服务 → 做诊断/巡检 → 控数据访问与发布 → 做备份与自动化 → 管用户和全局配置**。一级菜单承担业务域分组，二级/三级菜单承担具体任务，避免将“策略、记录、基础设施配置”混在同一页面。

系统菜单遵循三个原则：

1. **最小可见性**：菜单只有在用户拥有相应菜单权限时显示；菜单组至少包含一个可见子菜单才显示。
2. **最小数据范围**：可见菜单不等于可操作所有资源。非管理员还受集群级 `实例查看 / 查询 / 变更 / 执行` 权限约束。
3. **执行与留痕分离**：执行类菜单应提供目标、范围、预检查、状态和历史；记录/历史类菜单作为追溯入口，关键操作进入审计。

## 3. 全局页面交互规范

| 页面类型 | 统一设计要求 |
| --- | --- |
| 总览页 | 顶部提供关键指标和状态分布；筛选后统计、图表、列表必须使用同一结果集。 |
| 资产/配置列表 | 支持检索、筛选、分页、创建、编辑、启停/删除；敏感字段脱敏，变更需二次确认。 |
| 执行页 | 必须展示目标集群/实例、数据库/对象、权限、风险提示、超时和执行状态；提供可追溯执行 ID。 |
| 任务页 | 区分“定义/策略”“调度状态”“运行结果”；长任务采用异步状态和轮询，不阻塞页面。 |
| 历史/审计页 | 支持时间、操作者、对象、结果与关键字筛选；可查看失败原因和必要的上下文。 |
| 配置页 | 配置保存前校验必填项与关联关系；外部服务提供连通性测试；密钥仅允许写入，不回显明文。 |

## 4. 菜单详细设计

### 4.1 运行总览

| 菜单 | 权限 Key / 路由 | 功能设计 |
| --- | --- | --- |
| 运行总览 | `dashboard` / `/dashboard` | 登录后默认工作台。聚合实例运行状态、告警、备份、任务等核心态势，并提供快捷跳转。面向管理者、DBA 和运维做日常巡查。 |

### 4.2 资源管理

| 菜单 | 权限 Key / 路由 | 功能设计 |
| --- | --- | --- |
| 数据库申请 | `database_apply` / `/resources/database-apply` | 填写数据库资源需求，形成可追踪申请。应包含业务归属、环境、数据库类型、容量/规格、申请人和用途。 |
| 数据库回收 | `database_recycle` / `/resources/database-recycle` | 对不再使用的数据库资源发起或处理回收；设计上应明确资源范围、数据保留/备份前置条件、回收原因和执行结果。 |
| 申请流水 | `application_history` / `/resources/application-history` | 按状态、时间、申请人和资源类型查询全链路记录，承接申请与回收的审计追溯。 |

## 5. 权限与角色设计

### 5.1 权限判定流程

`登录态有效 → 菜单权限决定入口可见性 → 集群权限决定资源是否可列出/读取 → 查询、变更、执行接口再次鉴权 → 写入审计`

管理员默认拥有所有菜单和集群能力。普通用户的有效菜单来自“用户直配 + 角色组继承”，集群能力来自“用户直配 + 角色组 + 数据源权限组”的并集。权限配置页面应明确标注“直接授予、继承授予、生效权限”，防止误删继承权限。

### 5.2 推荐角色模板

| 角色 | 建议菜单 | 建议集群权限 |
| --- | --- | --- |
| 平台管理员 | 全部 | 全部 |
| DBA | 服务管理、巡检、诊断、备份、数据发布、配置中必要项 | 负责集群的实例查看、查询、变更、执行 |
| 运维 | 运行总览、服务管理、巡检、任务、备份记录、必要配置 | 实例查看与查询；变更按需授予 |
| 研发只读 | 运行总览、数据查询、历史记录、权限申请 | 指定集群查询 |
| 研发发布 | 数据查询、SQL 上线、工单历史、权限申请 | 指定集群查询/执行，变更按流程最小化授予 |

## 6. 核心闭环与菜单协同

| 场景 | 建议菜单路径 | 闭环结果 |
| --- | --- | --- |
| 新建数据库资源 | 数据库申请 → 申请流水 → 集群/实例管理 → 用户/数据源权限管理 | 资源、归属、访问范围和历史同时建立。 |
| 发现运行异常 | 运行总览 → 巡检状态 → 实例详情/连接管理 → 参数检查或慢查治理 | 从告警定位到实例与治理动作。 |
| 受控数据操作 | 权限申请 → 数据查询/数据变更 → 历史记录 | 先授权、再执行、后审计。 |
| 安全发布 | SQL上线 → 工单历史 → 结果查询 | 审核、执行、回滚线索和结果可追踪。 |
| 备份保障 | 工具/密钥/存储/Agent/通知配置 → 策略 → 备份记录/总览 | 基础设施、策略、任务和通知形成闭环。 |
| 跨系统接入 | SSO/JumpServer/MCP/AI/域名配置 → 对应业务菜单 | 外部能力受配置、权限和审计约束。 |

## 7. 实现边界和设计建议

1. 当前菜单的可见性完全依赖后端返回的权限；权限拉取失败时默认不展示菜单，这是安全优先的设计。
2. “实例详情、连接管理、会话探测”并非所有数据库类型都有相同入口，不能为了菜单一致性虚构未实现能力。
3. “智能分析”路由虽存在，但当前导航被注释；若启用，应放在“数据访问”下，并明确其与“SQL 上线 AI 初审”的差异。
4. “申请预览”路由当前不在菜单中，可作为申请提交后的过程页；若希望运营人员独立使用，建议纳入“资源管理”并配置单独权限 Key。
5. 建议为每一个执行类菜单统一补齐：前置校验、风险等级、二次确认、执行 ID、可取消状态、结果详情和审计链接。
6. 备份、AI、MCP、SSO、JumpServer、S3、阿里云 DNS 和 Agent 都依赖部署配置；菜单可见不代表外部依赖已通过生产验收。
